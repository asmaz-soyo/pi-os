# フェーズ2-90 新しい PC で見つかった不安定なテスト

## 何があったか

開発 PC を変えた(Ubuntu 24.04 の WSL2)。新しい PC で `cargo xtask ci` を回すと、QEMU virt の結合テストが通ったり落ちたりした。6 回回して、全部通ったのは 1 回だけだった。前の PC と GitHub Actions では通っていた。

落ち方は 3 つあった:

| テスト | 起きたこと |
| --- | --- |
| `programs_use_the_own_tcp_after_switching_the_default` | 送ったはずの文字列がサーバーに届かない(exit 1) |
| `a_realtime_task_wakes_on_time_despite_a_busy_task` | 遅れの最大が 5ms を超える(1.7〜9.7ms。前の PC は 0.3ms 以下) |
| QEMU 全体 | 62 件で 46〜53 秒かかり、`timeout 60` に届くことがある |

## 自作 TCP のテスト:カーネルではなく、テストの組み方の競合

OS を普通に起動し、同じスクリプトをシェルで 15 回くり返すと、10 回目で再現した。クライアントの nc は 0 で終わったのに、サーバーの nc は何も書かずに終わっていた。

BusyBox の nc(`networking/nc.c`)は、1 巡ごとに「標準入力 → ソケット」の順に読む:

- 標準入力が EOF なら `shutdown(SHUT_WR)` で FIN を送り、ソケットだけ読み続ける
- ソケットが EOF なら、標準入力が残っていても `exit_SUCCESS()` で終わる

テストのサーバーは `nc -l … < /dev/null` なので、つながるとすぐに FIN を送る。クライアントは `echo … | nc` なので、`echo` がパイプに書く前にその FIN が届くと、何も送らずに 0 で終わる。

```
サーバー nc:accept → stdin(/dev/null)が EOF → FIN を送る
クライアント nc:connect → poll → ソケットだけ読める(FIN)→ 何も送らずに終わる
echo:                                                 ← まだ書いていない
```

Linux でも同じになることを確かめた。ホストの `qemu-aarch64` で同じ BusyBox を動かし、`(sleep 1; echo hello) | nc` で書き込みを遅らせると、毎回「クライアント 0、サーバーは空」になる。前の PC が速かったので、たまたま echo のほうが先だっただけだった。

直したこと:送る中身を先にファイルに書き、`nc 127.0.0.1 7310 < /tmp/msg_own` で送る。普通のファイルは最初の poll から読めるので、nc は FIN を読む前に必ず中身を送る。受け取りの待ちも、`for` を 1000 回まわすのをやめ、サーバーの nc を `wait $server` で待つようにした(シグナルの作業でシェルの `wait` が動くようになった)。直したあと、ファイルから送る形で 40 回くり返して 40 回とも届いた。

smoltcp の版のテストは、サーバーを `sleep 2 | nc -l` にして標準入力を開けたままにしているので、この競合はない。

## ジッタのテスト:最大ではなく平均で判定する

この PC で目覚ましが働いているときの値は、平均 0.8〜1.6ms、最大 1.7〜9.7ms。ホスト(WSL2 と QEMU)がたまに止まると、その 1 回が最大に出る。最大の 9.7ms は、目覚ましがなくティック(10ms)でしか起こせないときの値(p2-21 で測った、最小 3.7ms、平均 6.7ms、最大 9.8ms)とほとんど同じで、最大では見分けられない。

平均なら見分けられる。目覚ましなしだと平均は 5ms を超えるので、上限を「平均 3ms」にした(`jitter rt 3000`。3 つめの引数を最大の上限から平均の上限に変えた)。

## QEMU 全体の制限時間

cargo の runner の `timeout 60` を `timeout 180` にした(`xtask` の `qemu_runner`)。この PC で全体が 50 秒ほどなので、3 倍ほどの余裕。止まったままのテストを止めるためのもので、短い必要はない。

## わかったこと

- 速いマシンでだけ通るテストは、「どちらが先か」を時間に頼っていることが多い。遅いマシンに移すと出てくる
- 再現したら、まずカーネルの不具合かどうかを Linux で同じことをして確かめる。今回は Linux でも同じになったので、カーネルではなくテストを直した
