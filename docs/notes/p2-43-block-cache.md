# フェーズ2-43 ブロックキャッシュ

## 何をしたか

- `kernel::block::cache::CachedDevice`:最近読んだセクタをメモリに残し、同じセクタはディスクから読み直さない
  - 書き込みはディスクにもそのまま書く(write-through)。キャッシュにだけあってディスクにないデータはない
  - いっぱいになったら、一番長く使われていないセクタを捨てる(LRU)。「使った順番 → セクタ」の表(`BTreeMap`)を別に持ち、捨てるものを O(log n) で選ぶ。捨てたセクタのバッファは使い回す
- virtio-blk のディスク(/dev/vda)を 256 セクタ(128KB)のキャッシュで包んで登録した(2 つのパーティションで共有)
- テスト:2 回目は読まない、書き込みがディスクとキャッシュの両方に入る、LRU で一番古いものが捨てられる

## つまずいたところ:キャッシュで遅くなった

最初の版は、捨てるセクタを選ぶのに全部(256 個)を見ていた(`min_by_key`)。CPython(約 8MB)を読むと 2 万セクタ近くがキャッシュに当たらず、そのたびに 256 個を見るので、QEMU の結合テストが 2.9 秒 → 4.5 秒に遅くなった。順番の表を足して 3.0 秒になった。

| | QEMU の結合テスト(virt) |
| --- | --- |
| キャッシュなし | 2.9 秒 |
| 最初の版(捨てるものを全部見て選ぶ) | 4.5 秒 |
| 順番の表で選ぶ | 3.0 秒 |

QEMU の virtio のディスクはホストのメモリなので、読み直しはほとんどただ。ここではキャッシュの得がなく、表を引く手間(デバッグビルド)だけが見える。読み込みが重い実機の SD カードで効くはず。

## まだのこと

- 書き込みをまとめて後で書く(write-back)。速くなるが、電源が切れたときにデータが消えうる(ジャーナルと合わせて考える)
- 大きなファイルを順に読むと、キャッシュが全部入れ替わってしまう(よく使う inode の表なども追い出される)
