# M3-02 ページテーブル

## 何をしたか

- `hal::mmu::MapFlags`:マッピングの属性(書き込み、実行、ユーザー、デバイス)
- `arch_aarch64::mmu`:
  - `leaf_descriptor`:属性から記述子のビットを組み立てる
  - `PageTable`:`map_page`、`map_range`(そろっている所は 2MiB ブロック)、`translate`、`unmap_page`
  - `TableMemory`:テーブルを置くメモリの抽象。テストでは `BTreeMap` を物理メモリに見立てる
  - `KERNEL_VBASE = 0xFFFF_0000_0000_0000` と `phys_to_virt` / `virt_to_phys`

## なぜ必要か

- ユーザープロセスごとに別のアドレス空間を持たせる(M4)、カーネルを higher half に置く(M3-03)、`mmap` を作る(M5)、のすべてがページテーブルの操作
- 記述子のビットを1つ間違えると、「なぜか読めない」「なぜか実行できる」という分かりにくい不具合になる。ホストのテストで1ビットずつ固定した

## 中で何が起きているか

### 仮想アドレスの分解(4KiB グラニュール、4 段)

```
 47      39 38      30 29      21 20      12 11         0
| L0 添字 | L1 添字 | L2 添字 | L3 添字 | ページ内オフセット |
```

L0 テーブルの物理アドレスを TTBR に入れておくと、CPU は L0 → L1 → L2 → L3 とたどって物理アドレスを得る。`translate` は同じ手順をソフトウェアでやる(テストと、後でユーザーのポインタを検証するのに使う)。

### 記述子の主なビット

| ビット | 名前 | 意味 |
| --- | --- | --- |
| 0 | Valid | 有効 |
| 1 | Table/Page | L0〜L2 では「次のテーブル」、L3 では「ページ」。0 ならブロック |
| 4:2 | AttrIndx | MAIR の何番目の属性か。0 = デバイス、1 = 通常メモリ |
| 6 | AP[1] | EL0(ユーザー)からも触れる |
| 7 | AP[2] | 読み出し専用 |
| 9:8 | SH | 共有可能性(マルチコアでキャッシュを一致させる) |
| 10 | AF | アクセスフラグ。0 だと最初のアクセスでフォールトする |
| 11 | nG | ASID ごとのマッピング(ユーザー空間) |
| 53 | PXN | EL1(カーネル)では実行しない |
| 54 | UXN | EL0(ユーザー)では実行しない |

- ユーザーのコードは PXN を立てて、カーネルからは実行できないようにする(カーネルがだまされてユーザーのコードを実行する攻撃を防ぐ)
- デバイスのレジスタは実行不可、キャッシュしない属性にする

### TLB

CPU は変換の結果を TLB にキャッシュする。マッピングを外したり変えたりしたら、TLB を無効化(`tlbi`)しないと古い変換が使われ続ける。`unmap_page` はテーブルを書き換えるだけなので、無効化は呼び出し側(アーキテクチャ依存の部分)で行う。
