# フェーズ2-79 待ち行列(2):ネットワークのソケット

## 何をしたか

### TCP と UDP(inet)

ソケットを待つ(accept、connect の完了、read、write の空き、recvfrom)タスクは、ネットワーク全体で 1 つの待ち行列 `NET_WQ` で眠る。

```text
待つ側(システムコール)                     起こす側
  wait_event(&[&NET_WQ], ..., || {              poll のスレッド:poll_all の 1 巡で何か動いた
      poll して、自分のソケットを見る             ↑ 受信の割り込みが poll のスレッドを起こす(p2-69)
  })                                             ↑ タイマー(再送など)の時刻に起きる
                                               システムコールの中の poll で何か動いた
                                                 (ループバックは、送った側の poll で相手に届く)
                                                          ↓
                                                    NET_WQ.wake_all()
```

ソケットごとに待ち行列を持つほうが無駄はない(関係のないタスクまで起こさない)。ただ smoltcp は「どのソケットの状態が変わったか」を教えてくれないので、全員を起こし、それぞれが自分のソケットを見直す。起こされても条件が満たされなければ、また眠る。

### AF_UNIX

待ち受け(`Listener`)ごとに待ち行列を 1 つ:

- accept は、つながってくるのを待つ。connect が列に積んだら起こす
- connect は、列がいっぱいなら空くのを待つ。accept が取り出したら起こす
- 待ち受けが閉じたら、印(`closed`)を立ててから起こす。connect は ECONNREFUSED

最初は「待ち受けへの参照の数が 1 になったら閉じた」と見ていたが(relax で回っていたときのやり方)、起こす側が数を減らす前に起こすと、起こされた側はまだ閉じていないと見て眠り込む。印を立ててから起こせば、起こされた側は必ず印を見る。

データの読み書きはパイプ(p2-78)なので、もう眠って待つ。

## 確かめたこと

- ホスト:今までの TCP・UDP・AF_UNIX のテスト(両方の TCP の実装で)
- QEMU:`nc -l` が accept で待っているあいだ `S (sleeping)`
- ジッタ(リアルタイムのタスクの遅れ):最大 0.16ms(待っているタスクが CPU を使わなくなった)
