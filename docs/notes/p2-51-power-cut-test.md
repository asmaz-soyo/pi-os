# フェーズ2-51 ジャーナル(3):電源断のテスト

## 何をしたか

- 電源断のまねをするディスク(`Crashing`):`budget` 回書いたら、それ以降の書き込みは黙って消える(書いたつもりでも残らない)
- テスト `a_power_cut_at_any_write_leaves_a_consistent_filesystem`:ext3 のディスクで一続きの操作(mkdir、create、3000 バイトの書き込み、rename、unlink)をする。全部で 162 回書くので、0〜162 回目のすべての切れ目で電源を切り、次を確かめる
  1. 電源が戻ったとしてマウントする(ジャーナルのリプレイが走る)
  2. `e2fsck -fn` がきれい
  3. それぞれの操作が「全部起きたか、何も起きていないか」:書き込みは 3000 バイト全部か 0 バイト、rename の前と後の名前が両方あることはない、/keep.txt は中身ごとあるか、ないか
  1 ブロック(1KB)は 2 セクタなので、ブロックの途中で切れる場合も含む

## テストが見つけた不具合

1. **「要リカバリ」の印とジャーナルの書き順**:コミットの後、「ジャーナルのスーパーブロックに『ここから読め』」→「ファイルシステムに『要リカバリ』の印」の順に書いていた。間で切れると、ジャーナルにデータがあるのに印がない(マウントは印を見てリプレイするので、そのトランザクションは失われる。e2fsck も指摘する)。印を先に立てるようにし、マウントでは印がなくてもジャーナルにデータがあればリプレイするようにした
2. **壊れたディレクトリで無限ループ**:電源が切れたあともカーネルは操作を続けるので、書いたつもりのディレクトリのブロックが実際は 0 のまま、ということが起きる。項目の長さ(rec_len)が 0 だと、ディレクトリをたどるループが先に進まず、テストが止まった。長さがおかしければ EIO を返すようにした(壊れたディスクに出会ったときのカーネルの守り)

## 確かめたこと

直した書き順をわざと元に戻すと、このテストが落ちる(テストがその不具合を捕まえられる)
