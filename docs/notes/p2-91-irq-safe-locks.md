# フェーズ2-91 割り込みと分け合うロック(lock_irqsave と、使われ方の検査、割り込みの中のヒープ)

## 何があったか

新しい PC で、QEMU の結合テストが 15 回に 1 回ほど止まった。止まったのは `the_uart_receive_interrupt_is_registered` の中で、このテストは `IRQS.counts()`(割り込みの表を読む)を呼ぶだけ。

```
起動のタスク(割り込みは許されている)
  IRQS.counts()
    handlers.lock()        ← 表のロックを取る
    (Vec を作っている)
        ── タイマの割り込み ──
        IrqTable::dispatch
          handlers.lock()  ← 同じロックを待つ。持ち主(起動のタスク)はこの割り込みが
                              終わるまで動けないので、いつまでも待つ
```

コアが 1 つなので、割り込みのハンドラが待っているあいだ、持ち主には順番が回らない。ADR-0007 からカーネルのスレッドと起動のタスクは割り込みを許したまま走るので、この形が起きるようになった。

## したこと

- **`lock_irqsave()`**:割り込みを止めてから取り、離したあと元に戻す。`irq_save` → ロックを取る →(使う)→ ロックを離す → `irq_restore` の順。離す前に割り込みを戻すと、離すまでのすきまに割り込みが来て同じことになる
- **割り込みの中かどうか**:`IrqTable::dispatch` が `irq_enter` / `irq_exit` で囲む。`sync::in_irq()` で分かる
- **使われ方の検査**(デバッグのビルドだけ):ロックごとに 2 つの印を持つ
  - 割り込みの中で取られた
  - 割り込みを許したまま取られた
  両方そろったらパニックする。止まるかどうかはタイミング次第でも、両方の使い方が一度ずつ起きれば必ず見つかる(Linux の lockdep が「IRQ-safe と IRQ-unsafe の両方で使われた」と知らせるのと同じ考え)
- **割り込みの操作の登録**:`sync::set_irq_ops` で BSP が登録する(止める・戻す・今許されているか)。前はスケジューラだけが `sched::Platform` に持っていたので、そちらは外して `sync` に一本化した。arch に `cpu::irqs_enabled()`(DAIF の I ビットを読む)を足した

## 検査で見つかったもの

検査を入れて QEMU で回すと、まず止まったテストとは別の `SCHED`(スケジューラ)で知らせた。`wake` は割り込みの中から呼ばれるが、`current()`、`running()`、`is_alive()`、`is_sleeping()`、`task_count()`、`sleep_until` の入口は割り込みを止めずに取っていた。カーネルのスレッドが `current()` を呼んでいるところへ virtio-net の割り込みが来て `wake` が呼ばれれば、同じように止まる。

コードを読んで、待ち行列(`WaitQueue::waiters`)も同じだと分かった。端末と GPIO の割り込みが `wake_all` を呼び、どの `wake_all` も `POLL_WQ` を起こすので、ネットワークの poll のスレッドの `wake_all` と重なる。QEMU のテストではたまたま両方がそろわなかったので、ホストのテストで両方を作って Red にしてから直した。

| ロック | 割り込みの中 | 割り込みの外(許したまま) | 直し方 |
| --- | --- | --- | --- |
| `IRQS.handlers` | `dispatch` | `counts`、`register` | 外は `lock_irqsave` |
| `SCHED` | `wake` | 問い合わせの関数 | 全部 `lock_irqsave`(`schedule` は切り替えをまたいで `irq_save`) |
| `WaitQueue::waiters` | `wake_all` | `wake_all`、登録、外す | 全部 `lock_irqsave` |

割り込みコントローラ(`B::intc()`)と `GPIO_CTRL` は、割り込みの外で取るのが起動のとき(割り込みを許す前)だけなので、そのままにした。

## 確かめたこと

- ホストのテスト:`lock_irqsave` が割り込みを止めて戻す、`irq_enter` と `irq_exit` のあいだは `in_irq`、割り込みの中と外の両方で取るとパニック、`lock_irqsave` ならパニックしない、`dispatch` のハンドラは割り込みの中で動く、割り込みの表と待ち行列は割り込みの中と外の両方から使える
- QEMU:qemu-virt と raspi3 の結合テストが、検査を入れたまま通る

## 割り込みの中のヒープ(検査が見つけた)

検査を入れて CI を回すと、スナップショット(シェルに `hello` と打つ)でパニックした。報告の場所はコンソール(`console.rs`)だったが、gdb でパニックの関数に止める点を置いて本当のバックトレースを取ると、最初のパニックはヒープのロックだった:

```
UART の受信割り込み → input_arrived → TTY_WQ.wake_all
  → 取り出した Vec<Tid> を捨てる → dealloc → ヒープのロック   ← 1 回目のパニック
      → パニックの報告がコンソールのロックを割り込みの中で取る ← 2 回目のパニック(これが表に出た)
```

ヒープのロックは、ふだん割り込みを許したまま取られる(カーネルのスレッドが確保する)。割り込みの中で確保・解放すると、同じ形で止まりうる。`heap.rs` にも「割り込みハンドラの中では確保しないこと」と書いてあったが、守られていなかった。

- `wake_all`:列を取り出して捨てる(`mem::take`)のをやめ、ロックを持ったまま `drain(..)` で空にする。入れ物は残るので解放しない。ロックの順番は「待ち行列 → スケジューラ」
- 実行待ちの列:`wake` の `push_back` は、列がいっぱいなら伸びる(確保する)。タスクを作るとき(割り込みの外)に、全部のタスクが並べるだけの場所を `RunQueue::reserve` で取っておく
- パニックの報告の最初に `sync::stop_lock_checks()` を呼ぶ。報告が検査でもう一度パニックして、最初の原因を隠さないように

QEMU のテスト(両方の BSP で動く `common_tests!`)を 2 つ足した。どちらも本物の割り込みを止めたうえで `irq_enter` で「割り込みの中」を作る。ヒープのロックは起動からずっと割り込みを許したまま使われているので、割り込みの中でヒープに触れば検査が必ずパニックする:

- 待っているタスクのいる待ち行列を `wake_all` する(直す前は `dealloc` でパニック)
- 止めたタスクを 40 個作り、まとめて `wake` する(直す前は `alloc` でパニック)

## ついでに直したもの

GPIO のスナップショット(`qemu-virt-gpio`)は、台本が QEMU のモニタに `system_powerdown` を打つタイミングで、モニタの改行が 1 行まざることがある(まざる位置は毎回ちがう)。`Hello from user space!` のあとと `svcman: button run 1 exited with 0` のあとに `...` を入れた。
