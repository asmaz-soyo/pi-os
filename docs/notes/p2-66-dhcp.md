# フェーズ2-66 ネットワーク(8):DHCP

## 何をしたか

- eth0 のアドレス、ゲートウェイ、DNS を DHCP でもらう(前のステップの決まった値をやめた)
  - `Stack::start_dhcp`:smoltcp の DHCPv4 のクライアントのソケットを足す。やりとり(DISCOVER → OFFER → REQUEST → ACK)は `poll` の中で進む
  - `Stack::poll` で DHCP の知らせ(`Configured` / `Deconfigured`)を見て、`Stack::apply` でインターフェースに当てる(アドレス、デフォルトルート、DNS)。借りたものを失ったら外す
  - `inet::attach` にアドレスを渡さなければ DHCP を使う
- `inet::dns_of`:もらった DNS サーバー
- テスト:ホスト(`apply` でアドレス・ルート・DNS が付き、失うと外れる)、QEMU(eth0 が QEMU のユーザーモードのネットワークから 10.0.2.15 と DNS 10.0.2.3 をもらう。外への TCP もそのアドレスで通る)

## つまずいたこと:カーネルのスレッドは途中で切り替わらない

DHCP を入れると、リアルタイムのタスクのジッタが 7.6ms になった(限度は 5ms)。測ってみると、DHCP のやりとりの間、smoltcp の 1 回の `iface.poll` に 1〜3ms かかり、それを続けて呼んでいた。

Pi-OS では、タスクの選び直しはユーザー空間に戻るときにしか起きない。カーネルのスレッド(poll のスレッド)は、自分から眠るまで走り続ける。そのあいだ、時刻になったリアルタイムのタスクも待たされる。

直したこと:

1. smoltcp だけ最適化してビルドする(`[profile.dev.package.smoltcp] opt-level = 2`)。自分たちのコードはデバッグしやすいまま
2. poll のスレッドは、1 回起きたら 1 巡だけ poll する。まだやることがあれば 1ms 後に起き直す(そのあいだに、ほかのタスクが動ける)

ロックを握ったまま切り替えるのはやめた。同じロックを待つ優先度の高いタスクが回り続け、ロックを持つタスクに順番が回らなくなる(spin::Mutex は待つあいだ CPU を手放さない)ため。

結果:ジッタの最大は 1.6ms。カーネルの中でも切り替えられるようにする(カーネルのプリエンプション)のは、後の宿題
