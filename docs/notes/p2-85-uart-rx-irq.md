# フェーズ2-85 待ち行列(4):端末の入力を UART の受信割り込みで起こす

## 何をしたか

端末の read は、今まで 10ms ずつ眠っては UART を確かめていた(p2-80)。QEMU virt では、PL011 の受信割り込みで起こすようにした。

```text
キーを打つ → PL011 の受信割り込み(GIC の 33 番)
             ハンドラ:受信割り込みを止め(IMSC = 0)、TTY_WQ を起こす
                        ↓
             端末を読んでいたタスク:UART を空にする(tty の行の編集、エコー)
                        読めるものがなければ、受信割り込みを戻して(IMSC = RX | RT)眠る
```

- PL011 の受信割り込みは 2 つ:FIFO が半分たまった(RX)と、データがあるまま 32 ビット分の時間が過ぎた(受信のタイムアウト、RT)。1 文字だけ打ったときは RT で知らされる
- **ハンドラは止めて起こすだけ**:受信の割り込みは、FIFO にデータが残っているあいだ立ち続ける。ハンドラで止めないと、読む側が動く前に何度でも割り込みが来て、先へ進めない。ハンドラの中で UART を読む(コンソールのロックを取る)と、ロックを持ったタスクに割り込んだときに止まってしまうので、読むのは起こされたタスク
- 割り込みを戻すのは、登録して UART を空にしたあと。戻したときにまだデータがあれば、すぐ割り込みが来て起こしてもらえる(起こしたことを失わない)
- マスクとクリアのレジスタ(IMSC、ICR)だけを触る窓口を、コンソールとは別に用意した(ハンドラがコンソールのロックを取らずに済むように)。割り込みの番号と触り方は BSP が持つ(`Board::UART_IRQ`、`Board::uart_rx_irq`)
- raspi3 は、UART0 の割り込み(GPU の割り込み 57 番)を受ける割り込みコントローラのドライバがまだないので、10ms ごとのまま(実機の段階で)

```
pi-os:/$ cat /proc/interrupts
           CPU0
  30:        171  timer
  33:          3  uart
```

## 確かめたこと

- ホスト:PL011 の受信割り込みを入れる・止める(止めるときは印も消す)
- QEMU virt:"uart" の割り込みが 33 番で登録されている。シェルに打ち込むスナップショットのテストが、割り込みの道で通る
- 手で:1 行打つたびに uart の回数が増える
