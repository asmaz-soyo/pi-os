# M2-01 例外ベクタとトラップフレーム

## 何をしたか

- `arch_aarch64::exception`:16 個の入口を持つベクタテーブルと、全レジスタを保存・復元する共通処理。Rust のハンドラ(`Handler` トレイト)へ `&mut TrapFrame` を渡す
- `arch_aarch64::trap::TrapFrame`:保存したレジスタの並び。表示すると全レジスタを出す
- `arch_aarch64::esr`:ESR(例外の原因)の解読。`brk #7`、`data abort (same EL): translation fault level 1, write` のように表示する
- `arch-aarch64` をホストでもビルドできるようにした。アセンブリの部分は `target_os = "none"` のときだけ。ESR の解読やフレームの並びはホストでテストする
- `fault-demo`:起動後に未定義命令(`udf #0`)を実行し、未処理の例外の報告をスナップショットで固定した
- カーネル内テスト:`brk` で例外を起こし、ハンドラが x0 を書き換えて次の命令から再開できることを確かめた

## なぜ必要か

- システムコール(`svc`)も、割り込みも、ページフォールトも、すべて「例外」として CPU から届く。M2 以降のすべての土台
- 例外から戻るときに「保存しておいたレジスタを書き戻す」仕組みがあるからこそ、システムコールの戻り値を x0 に入れたり、別のタスクに切り替えたりできる

## 中で何が起きているか

### 例外が起きると

1. CPU が `ELR_EL1` に戻り先、`SPSR_EL1` に元の状態、`ESR_EL1` に原因を書く
2. `VBAR_EL1 + オフセット` に飛ぶ。オフセットは「どこから来たか × 何が起きたか」で決まる(`exception.rs` の表)
3. 入口(0x80 バイト)で 288 バイトをスタックに確保し、x0・x1 を保存して、番号を x0 に入れて共通処理へ
4. 共通処理で残りのレジスタと `SP_EL0`・`ELR`・`SPSR`・`ESR`・`FAR` を保存し、`arch_exception_entry(番号, フレーム)` を呼ぶ
5. 戻ってきたら、フレームの値(書き換えられているかもしれない)を CPU に戻して `eret`

### トラップフレームの並び

| オフセット | 中身 |
| --- | --- |
| 0〜240 | x0〜x30 |
| 248 | SP_EL0 |
| 256 | ELR_EL1 |
| 264 | SPSR_EL1 |
| 272 | ESR_EL1 |
| 280 | FAR_EL1 |

アセンブリと Rust の構造体の並びがずれると、静かに壊れる。`offset_of!` を使ったホストのテストで、並びを固定している。

### ハンドラの差し替え

- `exception::set_handler` は前のハンドラを返す。テストでは一時的に自分のハンドラを入れ、終わったら戻す
- ハンドラを呼ぶ前にロックを離している。ハンドラの中で例外が起きても(例えば次の `brk`)固まらない
- ハンドラが登録されていない例外は、レジスタをすべて表示してパニックする

### arch をホストでテストできるようにした理由

ESR の解読や、M3 で作るページテーブルの記述子の組み立ては、CPU の仕様を表す「純粋な計算」。ハードウェアがなくても検証できる部分はホストで TDD したい。
