# M4-01 ELF の読み取り

## 何をしたか

- `kernel::exec::elf::parse`:静的リンクの AArch64 実行ファイルを検証して読み取る
- `Elf::segments`:メモリに置くセグメント(PT_LOAD)の一覧。権限は `MapFlags::USER_*` に変換する
- AT_PHDR(補助ベクタ。musl が起動時に自分のプログラムヘッダを探すのに使う)のために、プログラムヘッダの仮想アドレスも求める
- テストでは、小さな ELF のバイト列をその場で組み立てて使う(バイナリのファイルをリポジトリに置かない)

## なぜ必要か

ユーザープログラム(musl で静的リンクした qjs など)は ELF 形式。カーネルは「ファイルのどこを、メモリのどこに、どの権限で置き、どこから実行を始めるか」をここから知る。

## 中で何が起きているか

- ELF ヘッダ:先頭 4 バイトが `\x7fELF`、64 ビット・リトルエンディアン、種類が実行ファイル(ET_EXEC)、CPU が AArch64(183)であることを確かめる
- プログラムヘッダ:1つ 56 バイト。PT_LOAD が「ファイルの `offset` から `filesz` バイトを、仮想アドレス `vaddr` に `memsz` バイトの区画として置け」という指示。`memsz > filesz` の差は 0 で埋める(.bss)
- PT_INTERP(動的リンカの指定)があれば、まだ動かせないので `ENOEXEC`
- ファイルの外を指す、ユーザー空間(下位 48 ビット)の外に置こうとする、`filesz > memsz`、のような壊れた・悪意のある ELF も `ENOEXEC` で拒否する。カーネルは外から来たデータを信用しない

zig で作った musl の静的バイナリでは、PT_LOAD が4つ(読み出し専用、コード、RELRO、データ)、先頭のアドレスは `0x100_0000` だった。
