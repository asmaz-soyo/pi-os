# M4-02 ユーザーのメモリと、プログラムの読み込み

## 何をしたか

- `hal::mmu::AddressSpace`(プロセスのページテーブル)と `hal::mmu::PhysMemory`(フレームとその中身)のポートを足した
- `kernel::mm::user::UserMemory`:プロセスのユーザー空間
  - `copy_from_user` / `copy_to_user` / `read_cstr`:ユーザーのポインタは必ずここを通す
  - `map_zeroed` / `unmap`:ページの追加と削除
  - `load`:プログラムの読み込み用(読み出し専用のページにも書ける)
  - 破棄されると、マップしたフレームをすべて返す
- `kernel::exec::load`:ELF のセグメントを配置し、初期スタック(argc、argv、envp、補助ベクタ)を作る
- ホストのテストでは、偽のアドレス空間(`BTreeMap`)と偽の物理メモリ(`Box` のフレーム)を使った

## なぜ必要か

- CLAUDE.md のルール「ユーザー空間のポインタは必ず `copy_from_user` / `copy_to_user` を通す」の実装。ユーザーが `write(1, 0xdeadbeef, 10)` のような変なポインタを渡してもカーネルは落ちず、`EFAULT` を返す
- musl のプログラムは、起動時にスタックの決まった形(argc、argv、envp、補助ベクタ)を前提にしている。ここが1ワードずれるだけで、`main` に届く前に落ちる

## 中で何が起きているか

### copy_from_user の流れ

1. アドレスがユーザー空間(下位 48 ビット)の中か
2. プロセスのページテーブルで変換できるか(マップされているか)
3. 属性が「ユーザーから触れる」か。書き込みなら「書き込み可」か
4. 物理フレームを、カーネルの線形マップ経由で読み書きする。ページをまたぐときはページごとに分ける

どれかに失敗したら `EFAULT`。カーネルはユーザーの仮想アドレスに直接触らないので、フォールトが起きる余地がない。

### 初期スタック(高いアドレスから)

```
0x7fff_ffff_0000  STACK_TOP
                  AT_RANDOM の 16 バイト
                  "qjs\0" "hello.js\0" "HOME=/\0" …(文字列)
                  (16 バイト境界までの詰め物)
                  補助ベクタ:(AT_PHDR, …) (AT_PAGESZ, 4096) (AT_ENTRY, …) (AT_RANDOM, ptr) … (AT_NULL, 0)
                  envp[0], NULL
                  argv[0], argv[1], NULL
sp →              argc
```

- 補助ベクタは、カーネルからプログラムへの「追加の情報」。musl は AT_PHDR からプログラムヘッダを見つけて TLS(スレッドローカル変数)を準備し、AT_RANDOM をスタック保護の値に使う
- セグメントの終わり(ページ境界に切り上げ)を、ヒープ(`brk`)の始まりとして返す
