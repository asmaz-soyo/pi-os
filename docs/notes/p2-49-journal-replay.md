# フェーズ2-49 ジャーナル(1):マウントのときのリプレイ

## ジャーナルとは

ext2 は 1 つの操作(ファイルを作る)で、ディスクの何か所も書く:inode のビットマップ、inode の表、ブロックのビットマップ、ディレクトリのブロック。途中で電源が切れると、「ビットマップでは使用中なのに、どこからも指されていない inode」のような食い違いが残る(これまでは e2fsck に全部調べてもらうしかなかった)。

ジャーナルは、まとめて変えるブロックの新しい中身を先に別の場所(ジャーナル)に書き、最後に「コミット」の印を書く。そのあとで本来の場所に書く。

- コミットの前に切れた → ジャーナルのそのトランザクションはなかったことにする(本来の場所はまだ何も変わっていない)
- コミットの後に切れた → 次のマウントで、ジャーナルから本来の場所に書き直す(リプレイ)

どちらでも「全部変わったか、何も変わっていないか」になる。

## 何をしたか

- `kernel::fs::jbd`:Linux の ext3 / ext4 と同じ形式(JBD2)のジャーナルを読む。数値はビッグエンディアン
  - `JournalIo`:ジャーナルの n 番目のブロックを読み書きする、ファイルシステムの本来の場所に書く(ext2 の中身に頼らない)
  - `recover`:Linux と同じ 3 回の読み通し
    1. ログの始まり(`s_start`)から、記述ブロック → 中身 → コミットブロックをたどり、コミットまで書けているトランザクションの範囲を決める(番号 `h_sequence` が続かなくなったら終わり)
    2. 取り消しブロック(revoke)を集める:「このブロックは、これより前のトランザクションの中身を書き戻すな」
    3. 記述ブロックのタグごとに、中身を本来の場所に書く(取り消されたものは飛ばす。中身がたまたまジャーナルの印で始まっていて、書くときに 0 にしてあったら戻す)
  - 終わったらジャーナルを空にする(`s_start = 0`)
- ext2:スーパーブロックが「ジャーナルあり(has_journal)」かつ「要リカバリ(needs_recovery)」なら、マウントのときにリプレイし、「要リカバリ」の印を消す。ジャーナルは inode 8(`s_journal_inum`)の中
- テスト:`mke2fs -t ext3` で作ったディスクに、`debugfs` のジャーナルのコマンド(`jo`、`jw`、`jc`)で、本来の場所には書かずにトランザクションだけを書いておく(電源が切れた状態)。マウントしてから確かめる
  - コミット済みのトランザクションは本来の場所に書かれる
  - コミットしていないものは無視される
  - 同じブロックなら後のトランザクションが勝つ。取り消されたブロックは書かれない
  - 終わったら `e2fsck -fn` がきれい(ジャーナルが空で、「要リカバリ」の印がない)
