# フェーズ2-70 カーネルのプリエンプション

## 何をしたか

- カーネルを実行中に割り込み(タイマのティック、起こす時刻の目覚まし)が来たら、そこでタスクを切り替えられるようにした(ADR-0007)
  - `arch::exception::Handler::before_return_to_kernel`:EL1 で受けた IRQ のあと、戻る直前に呼ぶ。`boot` は `preempt_count() == 0` かつ切り替えが要れば `yield_now`
  - 割り込みの終わり(GIC の EOI)は dispatch で済ませてあるので、切り替えた先でも次の割り込みが来る。割り込みの TrapFrame は今のタスクのカーネルスタックに積まれていて、戻ってきたときにそこから続ける
- `kernel::sync::SpinLock` を自前の型にした。ロックを持っている数を `preempt_count` で数え、持っているあいだは切り替えない
  - ホストのテストは並んで走るので、数はスレッドごと(`thread_local!`)。カーネルでは全体で 1 つ
- `schedule` に、ロックを持ったまま切り替えようとしたら止まる確かめ(デバッグのビルドだけ)を入れた。今のテストでは一度も起きなかった

## テスト

- ホスト:ロックを持つと数が増え、離すと戻る(入れ子、try_lock も)
- QEMU(両方の BSP):譲らずに 2 秒回るカーネルのスレッドがいても、20ms 眠ったタスクが 50ms 以内に起きる。前は 1981ms 遅れた

## つまずいたこと:テストが実装の前に通った

最初のテストは、`yield_now` のあとに時刻を測り始めていた。切り替えられないと `yield_now` から戻るのは spinner が回り終わったあとなので、そこから 20ms 眠っても遅れない。「眠ると決めた時刻」を `yield_now` の前に取るようにしたら、ちゃんと失敗した(Red)。テストが実装の前に通ったら、テストのほうを疑う。

## つまずいたこと:「譲るまで動かない」に頼っていたところ

CI の実機用イメージのスナップショット(raspi3-hw)で、最初のユーザープログラムが入口でフォールトした(translation fault level 0。TTBR0 が空のテーブルのまま EL0 に入った)。

`spawn_user` は「タスクを作る → プロセスの表に入れる」の順で、コメントに「新しいタスクは、このタスクが譲るまで動かないので、ここで表に入れてよい」とあった。プリエンプションが入ると、そのあいだにタイマで切り替わり、子が先に動き出す。子は入口で自分のアドレス空間を表から探すが、まだないので、空のテーブルのままユーザー空間に入っていた。

`sched::spawn_paused`(止めたまま作る。`wake` で動き出す)を足し、表に入れてから `wake` するようにした。fork(`start_child`)はシステムコールの中(割り込みを止めている)なので起きないが、同じ形にそろえた。プリエンプションを入れると、「ここは切り替わらない」という暗黙の前提がすべて崩れる。

## 結果

QEMU virt のリアルタイムのタスクのジッタの最大:1.6〜6.1ms(揺れていた)→ 0.13ms。

## まだのこと

- システムコールの処理の中は、割り込みを止めたまま(切り替わらない)
- preempt_count はコアごとにする(マルチコアのとき)
