# ADR-0010: 割り込みと分け合うロックは lock_irqsave で取り、使われ方をデバッグのビルドで検査する

- 状態:採用
- 日付:2026-11-28

## 背景

ADR-0007 から、カーネルのスレッドと起動のタスクは割り込みを許したまま走る(システムコールの処理は、今も割り込みを止めて走る)。割り込みのハンドラも取るロックを、割り込みを許したまま取ると、持っているあいだに来た割り込みのハンドラが同じロックを待ち続ける。コアが 1 つなので、持ち主には二度と戻らない。

新しい PC(WSL2)で、QEMU の結合テストが 15 回に 1 回ほど止まった(`IRQS.counts()` を呼ぶテストの中)。調べると、同じ形のロックが 3 つあった:

- 割り込みの表(`IRQS.handlers`):`dispatch` は割り込みの中、`counts` と `register` は外
- スケジューラ(`SCHED`):`wake` は割り込みの中からも呼ばれる。`current`、`running`、`is_alive` などは割り込みを止めずに取っていた
- 待ち行列(`WaitQueue::waiters`):端末と GPIO の割り込みが `wake_all` を呼ぶ。どの `wake_all` も `POLL_WQ` を起こすので、カーネルのスレッド(ネットワークの poll)の `wake_all` とも重なる

止まるかどうかはタイミング次第なので、テストを何度回しても見つかるとは限らない。

## 決定

- `SpinLock::lock_irqsave()`:割り込みを止めてから取り、離したあと元に戻す。割り込みのハンドラも取るロックは、ハンドラの外ではこれで取る
- CPU の割り込みの操作は `kernel::sync::set_irq_ops`(止める・戻す・今許されているか)で BSP が登録する。スケジューラもこれを使う(`sched::Platform` から `irq_save` / `irq_restore` を外した)
- 割り込みの入口(`IrqTable::dispatch`)は `irq_enter` / `irq_exit` で「割り込みの中」を知らせる(`in_irq`)
- デバッグのビルドでは、ロックごとに「割り込みの中で取られた」「割り込みを許したまま取られた」の印を持つ。両方そろったらパニックする(Linux の lockdep の小さな版)。`#[track_caller]` で、パニックの場所はロックを取った呼び出し元になる
- ホストのテストでは、割り込みの状態をスレッドごとの作り物にする(`sync::test_irq`)。テストで割り込みの中と外を作り、検査がパニックすることで Red にできる

## 理由

- 全部のロックで割り込みを止める案:ネットワークの poll(数 ms)のあいだタイマも止まり、ADR-0007 で避けたことに戻る。割り込みと分け合うロックだけにする
- 検査を入れずに目で探す案:今回の 3 つのうち 2 つは、止まったところとは別のロックだった。両方の使い方が一度ずつでも起きれば、タイミングに関係なく見つかる検査のほうが確か
- リリースのビルドには検査を入れない(ロックごとに 1 バイトと、取るたびの読み書きが要るため)

## 影響

- 割り込みのハンドラから新しくロックを取るときは、そのロックのほかの使い手を `lock_irqsave` にする。忘れても、QEMU の結合テストで両方の使い方が起きればパニックで知らせる
- 検査は「両方の使い方が実際に起きた」ときにしか知らせない。テストで通らない道は、今までどおり目で確かめる
- 割り込みのハンドラの中ではヒープを使わない(確保も解放も)。ヒープのロックも割り込みを許したまま取られるので、検査が知らせる。待ち行列は入れ物を残して空にし、実行待ちの列はタスクを作るときに場所を取っておく
- パニックの報告の最初で検査をやめる(報告が割り込みの中でコンソールに書いて、もう一度パニックしないように)
